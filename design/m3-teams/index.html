Teams GA shape (M3) — visual mockups

Static HTML mockups for the multi-team milestone of the team-memory SaaS plan (docs/saas-plan.md). No JavaScript, no backend; open states are rendered statically. Design tokens and component classes are extracted from the real Human Portal (web/src/styles/) with identical class names.

01 — Onboarding (no membership)

Post-login landing: create a team or join with an invitation token.

02 — Team switcher

Portal sidebar with the new TeamSwitcher popover, statically rendered open, plus the collapsed-sidebar variant.

03 — Team settings

General / Members / Invitations tabs, all rendered stacked on one page.

04 — Agent credentials (per team)

Team-scoped agent list, credential and enrollment cards, issued-secret state.

User flow

Sign in (WorkOS) → no team → 01 onboarding (create a team or accept an invitation) → portal with 02 team switcher in the sidebar → 03 team settings (members, invitations, danger zone) → 04 per-team agent credentials.

Frontend-state implications (for later implementation)

  • Today HumanMe carries a single membership; classify() in web/src/auth/AuthContext.tsx reduces it to no-membership / member states.
  • Multi-team changes that to multiple memberships + an active team: the auth state must hold the membership list and the currently selected team, and re-classify when the active team changes.
  • Every scoped query (agents, credentials, members, invitations) must be re-fetched — or keyed — by the active team, so switching teams invalidates cached lists.
  • The active team should persist across reloads (e.g. localStorage, like portal.side-collapsed) and be sent to the API as the requested scope.
